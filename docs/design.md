# 設計メモ

世帯向けの冷蔵庫リスト + 買い物リスト + レシピ集の Web アプリ。エージェントは内蔵せず、利用者が自分の Claude などからリモート MCP で読み書きする。アプリはデータの置き場に徹する。

プロトタイプ（`legacy/`）での実際の使われ方が出発点になっている。

- 一番使われているのは冷蔵庫リスト。目的は買い足しの防止と、家族間の共有（家にいる人が更新し、外出中の人がスーパーで見る）。
- 期限と数量は管理していない。
- 内蔵エージェントの「何が作れるか」の提案は合わずに使われなくなった。Claude + MCP で良くなるかは仮説。
- レシピは、リンクと自由テキストだけで持つ（段階 1〜2）。分量や材料の構造化（段階 3）は、使われ方を見てから決める。

## 方針

| 項目 | 決定 |
|---|---|
| 名前 | おかって（`okatte`）。台所の古い言い方「お勝手」から。勝手口のように、アシスタントが裏から出入りする |
| 対象 | 技術者が自分の世帯用にデプロイする（セルフホスト） |
| 文書の言語 | README とドキュメントは日本語 |
| ライセンス | MIT |
| 言語・基盤 | TypeScript、Hono、Vite + React の PWA、Drizzle + SQLite |
| 配備 | 第一は Cloudflare（Workers + D1、Free 枠で収まること）、第二は Docker + SQLite |
| 認証 | パスキーのみ。パスワードは持たない |
| MCP 認証 | アプリ自身が OAuth 認可サーバー（DCR、PKCE）。外部 IdP は使わない |
| MCP ツール | RESTful な粒度（リソースごとの list / get / create / update / delete） |

### Cloudflare Free に収める根拠（スパイクの実測）

- 公式 MCP SDK（zod + ajv）はバンドル 1.5 MiB で、アイドル後の最初の呼び出しが 20〜50 ms CPU かかり、上限の 10 ms を超えた。自前の薄いハンドラー（zod/mini、`tools/list` はビルド時に JSON 生成）にすると、バンドル 205 KiB、アイドル後でも中央値 3 ms、95 パーセンタイル 9 ms になった。
- 認可サーバー（約 385 行）も実機で、`/oauth/register` 3〜8 ms、`/oauth/authorize` 2〜6 ms、`/oauth/token` 5〜13 ms（初回のみ 13 ms）、`/mcp` 2〜12 ms。
- そのため、MCP SDK は使わず、`zod/mini` の自前実装を使う。

## 認証

### 利用者のログイン（PWA）

- WebAuthn のパスキーのみ。利用者ごとに複数のパスキーを登録できる。検証には `@simplewebauthn/server` を使う。
- パスキーは発見可能な資格情報（ログイン時にユーザー名を聞かない）で、端末でのユーザー確認（生体認証や PIN）を必須にする。アテステーションは求めない。
- 認証の途中経過（チャレンジ）は DB に保存し、5 分で失効、1 回使うと消える。最初の管理者の世帯名や、招待の内容は、チャレンジに紐づけてサーバー側で持つ。
- セッションは Cookie（トークンはハッシュで保存）。有効期間は 30 日。最後のパスキーは削除できない。

### 初回と家族の追加

1. **最初の管理者**: 最初にセットアップ画面を完了した人が管理者になる。競合は `app_meta` の一意キーで防ぐ（先に挿入できた方だけが成功）。任意のシークレット `SETUP_TOKEN` が設定されていれば、セットアップ画面でその入力を必須にする。未設定なら「最初のアクセス者が管理者」。
2. **家族の追加**: 管理者が招待リンクを発行し（有効期間 7 日、1 回限り、DB にはハッシュで保存）、本人の端末でパスキーを登録する。
3. **使えるパスキーを全て失った時**（他の端末のパスキーが残っていれば、その端末でログインして追加・削除するだけでよい）: 管理者が、その利用者向けの再登録リンクを発行する（`invites.user_id` を指定）。リンクを使っても利用者は同じ人のまま（ID、履歴、役割は変わらない）で、その利用者の既存のパスキー、セッション、MCP のトークンはすべて失効し、新しいパスキーだけが残る（紛失した端末で入れないようにするため）。管理者自身が全てのパスキーを失った場合は、運用者がコマンドで再登録リンクを発行する。
4. 先に他人が管理者になってしまった場合の復旧は、DB の `users` 系テーブルを空にして、やり直す（README に手順を書く）。再デプロイだけでは D1 のデータは消えない。

### Web API（PWA 向け）

- 設定は環境変数 `PUBLIC_URL`（必須。パスなしのオリジン。https のみ、localhost は http も可）、`SETUP_TOKEN`（任意）、`APP_NAME`（任意）。RP ID とオリジンは `PUBLIC_URL` から導き、`Host` ヘッダーは信用しない。
- セッション Cookie: `HttpOnly`、`SameSite=Lax`（claude.ai から同意画面へのリンクで Cookie が付くように。Strict は使えない）、https では `Secure` と `__Host-` 接頭辞。localhost の http では接頭辞と `Secure` を外す。
- CSRF: 状態を変える要求（GET/HEAD/OPTIONS 以外）は `Origin` が `PUBLIC_URL` と完全に一致しなければ 403。本文は `application/json` のみ（クロスサイトのフォームでは送れない）。
- 全レスポンスに `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`frame-ancestors 'none'`、`Referrer-Policy: same-origin`。`/api` は `Cache-Control: no-store`。
- エラーは `{ "error": "…" }` で、`invalid`→400、`unauthorized`→401、`forbidden`→403、`not_found`→404、`conflict`→409。想定外の例外は 500 の「Internal error」のみで、詳細はログに出す。
- レート制限は未実装。パスキーには推測できる秘密がないが、`/api/login/options` などの乱用対策は、デプロイ先（Cloudflare のレート制限など）に任せる想定。

### MCP の認可（OAuth 2.1）

- メタデータ: RFC 8414（認可サーバー）と RFC 9728（保護リソース）。`resource` パラメータ（RFC 8707）は、このアプリの `/mcp` のみ許可する。
- クライアント登録: DCR（RFC 7591）。公開クライアントのみ（PKCE S256 必須、client secret なし）。事前登録のクライアントは設定で持てるようにする。CIMD は、クライアント側の対応が確認できるまで保留する。
- 認可コードは 1 回限り、保存はハッシュ、有効期限は 5 分。
- アクセストークン（1 時間）とリフレッシュトークン（30 日、回転）は不透明な文字列で、DB にはハッシュで保存する。
- スコープは `read`（閲覧）と `write`（追加、変更、削除、移動）の 2 つで、`write` は `read` を伴う。どのツールも、今後足すツールも、このどちらかに入れ、新しいスコープは作らない。ChatGPT はアプリ作成時に検出したスコープを保存して要求し続け、スコープが増えるとアプリの削除と追加し直しが要るため（Asana の MCP も、許可は今後のツールを含むとしている）。削除は日常の操作であり、承認の要否は、クライアント側のツール単位の設定と `destructiveHint` に任せる。
- クライアントが要求したスコープは上限として扱う。指定がなければ両方、`write` を含めば両方、`read` だけなら閲覧のみ。知らないスコープだけなら `invalid_scope`。実際の許可は同意画面で本人が選ぶ。閲覧のみの接続が書き込みツールを呼ぶと、設定で接続し直せば編集もできる、と答える。設定画面の接続一覧に「閲覧と編集」か「閲覧のみ」を表示する。
- MCP に出さないもの: 家族の管理、招待、パスキー、データの一括削除。悪用されると困るため。将来出すなら、別のスコープにして初期状態では使えないようにする。
- `/mcp` をブラウザで開いた人（`Sec-Fetch-Mode: navigate`。MCP クライアントは送らない）は、`/assistants` へ送る。URL をアシスタントに渡さず開いてしまった時のため。
- リダイレクト URI は https か、ループバックの http（`localhost`、`127.0.0.1`、`[::1]`）のみで、フラグメント不可。登録されたものと完全一致を要求する。クライアントやリダイレクト URI の誤りには、リダイレクトせずエラーを表示する。それ以外の誤りは、`error`、`state`、`iss`（RFC 9207）を付けてクライアントへ返す。
- 認可の流れ: クライアントが `GET /oauth/authorize` へ飛ばす → 検証して `/authorize?<同じクエリ>`（PWA の同意画面）へ 302 → 未ログインならパスキーでログイン → 同意画面が `GET /api/oauth/authorization` で内容を取得し、`POST /api/oauth/authorize`（`decision: allow | deny`）の結果の `redirectTo` へ遷移する。同意の POST は Cookie 認証の Web API なので、同一オリジン検査（CSRF 対策）が効く。
- 同意画面は、クライアント名と、リダイレクト先のホストを表示する（名前は自己申告のため）。編集まで要求されたら「閲覧と編集（おすすめ）」と「閲覧のみ」から選ばせ（`POST /api/oauth/authorize` の `readOnly`）、今後増える機能も含むことを書く。
- 設定画面に、接続中のセッション一覧と取り消しを置く（`GET /api/connections`、`DELETE /api/connections/:id`。自分の接続のみ）。取り消すと、そのクライアントのアクセストークンとリフレッシュトークンが即座に無効になる。
- DCR は認証なしで登録できるため、登録数に上限（100）を設ける。トークンを一度も発行されなかったクライアントは 7 日後に消し、上限に達した時は、その中で最も古いものを消して空ける。全てが使用中なら登録を断る。Claude は接続のたびに `register` を 2 回呼ぶ。
- リフレッシュは同じ行のハッシュを回転させる（同時の 2 回目は失敗する）。盗まれたトークンの再利用検知（古いリフレッシュトークンの再提示で全体を失効させる）は行わない。
- CORS: メタデータ、`/oauth/register`、`/oauth/token`、`/oauth/revoke`、`/mcp` は任意のオリジンから呼べる（Cookie を使わないため）。`/oauth/authorize` と `/api` は同一オリジンのみ。
- 事前登録のクライアントは `createOAuthService` の `clients` で渡す（使われた時に DB へ反映される）。環境変数からの読み込みは、エントリポイントを作る時に足す。

### Web UI（PWA）

- `web/`: Vite + React + wouter。ビルドは `pnpm build`（出力は `dist/web`）。開発は `pnpm start`（API。`PUBLIC_URL=http://localhost:5173`）と `pnpm dev:web`（`:5173`、API へプロキシ）。パスキーはブラウザから見えるオリジンに結びつくため、この組み合わせにする。
- 画面: セットアップ（`/setup`）、招待・再登録（`/join/:token`）、ログイン（`/login`）、リスト（`/` と `/?list=fridge`）、レシピ（`/recipes`、`/recipes/new`、`/recipes/:id`）、設定（`/settings`）、接続の同意（`/authorize`）。未ログインで開くと `/login?next=…` へ送り、ログイン後に戻す（`next` は同一サイトのパスのみ）。
- 上部（家の名前、右上の歯車、タブ）は、ログインして使う画面すべてで同じで、画面の上に固定する。タブ（買い物、冷蔵庫、レシピ）はリンクで、場所は URL に残る（再読み込みや戻るで同じ画面に戻る）。設定は歯車から開き、設定でもう一度歯車を押すと閉じて、開く前の画面に戻る（歯車が設定の履歴に開いた元の画面を書いておき、あれば履歴を戻る。アドレスやログイン後に開いた設定では買い物リストへ）。ログイン、セットアップ、招待、接続の同意は手順の途中なので上部を出さない。
- 設定とレシピの詳細・追加・編集は、上部の下に自分の見出しを持ち、設定では歯車が、レシピの画面ではレシピのタブが選ばれた表示になる（画面の中に「戻る」は置かない）。タブは、そのタブで最後に開いていた画面を開く（レシピを開いたまま買い物に移り、レシピに戻ると同じレシピ）。今いるタブを押すと、リストとレシピ一覧では先頭に戻って再読み込みし、レシピの画面では一覧（最後の絞り込みのまま）に移る。覚えておくのはアプリを開いている間だけ（再読み込みで忘れる）。
- リスト: 買い物と冷蔵庫のタブ。各項目の右端に編集（鉛筆）と削除（ゴミ箱）。チェックは状態の切り替えだけで、リスト間は動かさない（画面から動かすのは、チェック済みの「まとめて…へ移す」だけ。1 件ずつの移動はアシスタントの `move_item`）。チェックは即座に反映し、失敗したら再読み込みで戻す。20 秒ごと、および画面に戻った時に再読み込みして、他の端末やアシスタントの変更を反映する。
- レシピ: 料理名と材料などの文字での検索（入力の 250 ms 後）、タグ（複数選ぶと AND）と本での絞り込み（`/recipes?tag=…&book=…`、URL に残る）、追加、詳細（出典、タグ、メモ、作った記録）、編集、削除。追加と編集では、既存の本を候補から選べ、既存のタグを押して付け外しできる。本の名前の変更と削除は、本で絞り込んだ時のメニューから。「作った」は、ブラウザのその日の日付（変更可）とひとことで記録する。
- 設定: 接続中のアシスタントの一覧と解除、アシスタント連携のページへの入口、自分のパスキーの追加・削除、家族の一覧、招待リンクの作成（管理者）、メンバーのパスキー再登録リンク（管理者）、ログアウト。
- アシスタント連携（`/assistants`）: つなぐと何ができるかを、アプリストアのスクリーンショットのように見せて、つなぐ気にさせるページ。設定から入る。見出し（「話しかけるだけで、{家の名前}のリストが動く」）、横にスワイプするカード（頼み方とアシスタントの返事の例を、チャットの画面のように見せる。写真や URL を添える例は、写真やリンクのプレビューとして描く。会話を主役にし、その下に何をしてくれたかを一文で添える。写真から、買い足し、レシピ、献立、振り返り。頼み方はコピーできる。返事は作り例）、Claude と ChatGPT へのつなぎ方（接続の名前は家の名前にする。Claude は公式の、カスタムコネクタの追加画面を名前と URL 入力済みで開くリンク〔`claude.ai/customize/connectors?modal=add-custom-connector&connectorName=…&connectorUrl=…`、本人が確認して追加する〕と、アプリから追加する時の URL。ChatGPT は入力済みで開く方法がなく、アプリからは追加できないため、ブラウザ（Android もあるので Safari に限らない）での手順。手順は ChatGPT のフォームの言葉（「接続タイプ」の「サーバーURL」、その下の欄など）で書き、ChatGPT を開くボタンは最初の手順に、URL はリンクや入力欄でなくコピーする文字として、それぞれ使う手順の中に置く。案内を開いている間は接続の一覧を 3 秒ごとと、画面に戻った時に見直し、開いた時になかった接続が現れたら、案内に代えて「接続できました！」と許可の範囲を出す。その下に、まず聞く一言を 2 つ、コピーできる形で出す〔「{家の名前}の冷蔵庫に何がある？」は、空のことがなく閲覧のみでも動くので、つながったことの確認に。「{家の名前}のリストで何ができる？」は、`instructions` に沿ってその家に合った頼み方を返させる。どちらも接続の名前を含め、アシスタントがツールを使いやすくする〕。15 分で見るのをやめる）、安心材料（閲覧のみを選べる、いつでも解除できる、家族の管理やパスキーには触れない）。縦に長くしないため、例は横に並べる。
- 同意画面: クライアント名、戻り先のホスト、許可する内容を表示する。名前は自己申告であることも書く。
- PWA: マニフェスト、アイコン（`scripts/make-icons.ts` で生成）、Service Worker（アプリ本体のみキャッシュ。`/api`、`/oauth`、`/mcp` は常にネットワーク）。リストのオフライン閲覧と書き込みは未対応。
- 静的ファイルの配信: Node 版は `src/http/static.ts`（SPA のフォールバックつき。`WEB_DIR` で場所を変更）。Workers 版は静的アセット（`not_found_handling: single-page-application`、API は `run_worker_first`）。どちらも CSP などのヘッダーを付ける（Workers 版は `web/public/_headers`）。
- 文言は日本語のみで、コンポーネントに直接書いてある。多言語化は未対応（OSS 公開時の言語の方針は未決）。

### 実行とデプロイ

- エントリポイントは 2 つ。`src/worker.ts`（Cloudflare Workers + D1）と `src/node.ts`（Node + SQLite ファイル。`pnpm start`）。どちらも `src/main.ts` の `buildApp(db, env)` でサービスをつなぐ。
- 設定: `PUBLIC_URL`（必須）、`SETUP_TOKEN`、`APP_NAME`、`OAUTH_CLIENTS`（事前登録クライアントの JSON 配列 `[{clientId, name, redirectUris}]`）。Node ではさらに `DATABASE_PATH`（既定 `./data/app.db`）と `PORT`（既定 8787）。Workers では vars / secrets。ローカルの Workers は `.dev.vars`。
- スキーマは `drizzle/` の SQL。どちらの版も、まだ当てていないものを自分で当てるので、デプロイや更新に別の手順は要らない。
  - Node は起動時に当てる（`_migrations` で記録）。
  - Workers はファイルを読めないため、`pnpm gen` で SQL を `src/db/migrations.generated.ts` に埋め込む（作り忘れるとテストが失敗する）。アイソレートごとの最初の要求で、1 つずつ D1 の `batch`（全部成功するか全部取り消す）で当てる。記録は `wrangler d1 migrations apply` と同じ `d1_migrations` 表に同じ形で書くので、wrangler のコマンドと食い違わない。何もない時は 1 往復で済む。2 つのアイソレートが同時に当てようとした場合は、後の方の `batch` が取り消され、記録を見直して先に当たっていれば続ける。失敗したら 500 を返し、次の要求でやり直す。
- ローカルの Workers: `.dev.vars` に `PUBLIC_URL=http://localhost:8787` → `pnpm dev`。
- `pnpm e2e`: 実際の HTTP で、セットアップ（ソフトウェアのパスキー）→ クライアント登録 → 同意 → トークン → MCP 操作 → リフレッシュ → 接続の取り消しまでを通す。引数なしだと Node 版を一時 DB で起動して検査する。`BASE_URL=http://localhost:8787 pnpm e2e` で、起動済みの `wrangler dev` などを検査する（その `PUBLIC_URL` は同じ URL で、世帯が未作成であること）。
- 確認済み: Node 版、`wrangler dev --local`（workerd + ローカル D1）、実際の Cloudflare（workers.dev、D1）の 3 つで `pnpm e2e` が通る。`nodejs_compat` は不要。Worker の起動時間は 19 ms。
- 更新: デプロイした時点の版から先へ進めるのは、利用者の GitHub と Cloudflare の側で行う。アプリには自分を書き換える権限（Cloudflare の API トークン）を持たせない。Workers の編集権限はアカウント全体にしか絞れず、アプリが乗っ取られた時の被害がデータからアカウントの Worker 全体に広がるため。また、元のリポジトリのリリースを確認なしに本番へ入れる形も取らない。
  - 版: `package.json` の `version` だけに書く（セマンティック バージョニング、0.1.0 から）。サーバーは `src/version.ts` から MCP の `serverInfo` に、画面はビルド時に設定の一番下に出す。
  - リリースの手順: `npm version minor -m "Release v%s"`（または `patch`。`package.json` を書き換え、コミットとタグ `v<版>` を作る）→ `git push origin main v<版>` → GitHub Actions（`.github/workflows/release.yml`）が、タグと `package.json` の一致、型チェック、テスト、ビルドを確かめてリリースの下書きを作る → 下書きの説明を日本語で書き（互換をなくす変更を先頭に）、公開する。下書きのうちは、各家の更新確認には見えない。
  - 予定の流れ: 公開のたびに版のタグと GitHub のリリースを作る → アプリは、管理者が設定を開いた時に最新のリリースを 1 日 1 回まで確認し、新しければ管理者にだけ知らせる（環境変数で止められる。家のデータは送らない）→ 「更新する」は利用者のリポジトリの GitHub Actions（手動実行のワークフロー）を開き、ワークフローが最新のリリースを取り込む → Cloudflare の自動ビルドがデプロイし、DB は起動時に整う。
  - 未確認: Deploy to Cloudflare ボタンが作る複製がフォークか、そのリポジトリが最初から Cloudflare の自動ビルドとつながるか、ワークフローのファイル自体が変わる更新を GitHub Actions の標準のトークンで取り込めるか（できない場合は手順を書く）。
- 実機の CPU 時間（2026-10-17、Free プラン、`wrangler tail` の `cpuTime`、`scripts/measure.ts` で 20 ラウンドを間隔 0.4 秒で実行した 173 件）。単位は ms:

  | 要求 | p50 | p90 | 最大 | 10 超 |
  |---|---|---|---|---|
  | `POST /mcp`（tools/call） | 4 | 6 | 10 | 0/18 |
  | `POST /oauth/token` | 4 | 5 | 9 | 0/38 |
  | `POST /oauth/register` | 7 | 10 | 12 | 1/20 |
  | `POST /api/logout` | 5 | 8 | 13 | 1/20 |
  | `POST /api/login/options` | 3 | 6 | 10 | 0/15 |
  | `POST /api/login/finish`（パスキー検証） | 9 | 11 | 20 | 3/20 |
  | `POST /api/oauth/authorize`（同意） | 11 | 15 | 15 | 13/20 |
  | `GET /api/items`（セッション認証 + 一覧） | 10 | 14 | 15 | 9/20 |
  | `POST /api/setup/finish`（登録検証、1 回） | 15 | | | |
  | `POST /api/setup/options`（コールドスタート直後、1 回） | 43 | | | |

  - 173 件中 28 件が 10 ms を超えたが、全て `outcome: ok` で、CPU 超過のエラーは出なかった。Free プランの 10 ms は、この範囲では打ち切りに使われていない（保証はない。設計は余裕のある側に倒しておく）。
  - 意外な点: 単純な `GET /api/items`（セッション認証と一覧）が p50 10 ms で、MCP の `tools/call`（4 ms）より重い。認証の問い合わせ（セッション → 世帯・利用者の結合）に原因がありそう。最適化の候補（未調査）。
  - 同意（`/api/oauth/authorize`）はセッション認証 + クライアント参照 + コード発行で、同じ理由で重い。
  - 原因（2026-10-17 に判明）: 認証のミドルウェアが `GET /items` で 2 回動いていた（Hono の `/items/*` は `/items` にも一致するため、`/items` との両方に付けていた）。セッション認証も 2 問い合わせ（セッション → 人物）だった。同意はクリーンアップが 3 回の別往復だった。
  - 対応: ミドルウェアを 1 回に、セッション認証を結合 1 問い合わせに、同意のクリーンアップとコード発行を 1 回の `batch` にした。`GET /api/items` は 5 → 2 文、同意は約 8 → 約 5 文。D1 は 1 往復ごとに CPU を使うので、`src/http/cost.test.ts` が代表的な要求の文数を固定している（増えたらテストが落ちる）。
  - 修正後の実機（本番、普段の操作を 19 件）: `GET /api/items` 2〜6 ms（修正前は p50 10 ms）、`GET /api/me` 1〜2 ms、`PATCH`/`move` 4〜7 ms。一方、アイドル後の最初の要求（コールドスタート）が 17〜25 ms（`/api/me` 18、`/api/connections` 17、`/mcp` 17 と 25）で、これは文数を減らしても変わらない。
  - コールドスタートの実測（測定用 Worker に旧版と新版を交互に 5 回ずつデプロイし、デプロイ直後の最初の要求の CPU を比較）:
    - どの経路も、コールドで中央値 12〜16 ms（最大 20〜48 ms）。ウォームは 1〜5 ms。起動時のコード読み込みが支配的で、バンドルは約 1.1 MB（`@simplewebauthn/server` の依存が大きい）。
    - **WebAuthn ライブラリの遅延読み込みは逆効果**だった（`/api/login/options` のコールドが中央値 16 → 65 ms、最大 112 ms。ウォームでも 46 ms）。Workers では動的 import が高くつく。採用しない。
    - `minify` は、5 回の測定ではノイズの範囲（中央値 15 → 12〜15 ms）で、効果を示せなかったので採用しない。
  - 結論: 暖まった状態は 10 ms 以内に収まっている。残るコールドスタートの 10〜20 ms は、バンドルの縮小（依存の見直し）以外に手がない。Free プランは、この超過で要求を止めていない（保証はない）。有料プランにすれば、この問題は消える。

## データモデル

世帯ごとに完全に分離する。全ての業務テーブルに `household_id` を持つ。ID は ULID（26 文字、時刻順に並ぶ）。時刻は Unix 秒の整数。

### アイテム（`items`）

| 列 | 内容 |
|---|---|
| `id` | ULID |
| `household_id` | 世帯 |
| `list` | `shopping` または `fridge` |
| `status` | リストごとの状態名（下表） |
| `name` | 品名（1〜500 文字） |
| `note` | 自由テキスト（任意）。レシピ名や URL の一言メモは、ここから始める |
| `added_by` | 追加した利用者 |
| `created_at`, `updated_at` | 時刻 |

プロトタイプの `checked`（リストごとに意味が変わる真偽値）はやめて、状態名にする。`(list, status)` の組み合わせは CHECK 制約で縛る。

| list | status | 意味 |
|---|---|---|
| `shopping` | `to_buy` | 買う物 |
| `shopping` | `bought` | 買った（スーパーで、残りと見分けるために残す） |
| `fridge` | `in_stock` | 在庫あり |
| `fridge` | `used_up` | 使い切り |

### 状態の変更と移動

- **状態の変更はリストを移動しない。** 買い物でチェックしても冷蔵庫には入らない。使い切りにしても買い物リストには出ない。
- リスト間の移動は、明示の操作（`move_item`）だけ。同じ行の `list` と `status` を変えるので、履歴は引き継がれる。移動先の状態は、買い物へは `to_buy`、冷蔵庫へは `in_stock`。
- 数量と期限は持たない。

### 変更履歴（`item_events`）

追記専用。仮説検証（繰り返し買う物、調理の頻度）と、Claude が「何をよく買い足すか」を提案する材料にする。アイテムが削除されても残すので、`item_id` に外部キーは付けず、品名のスナップショットを持つ。

- `type`: `created`、`renamed`、`status_changed`、`note_changed`、`moved`、`deleted`
- `data`: 変更の内容（JSON。例: `{"from":"in_stock","to":"used_up"}`）
- `source`: `web` または `mcp`、`client_id`（MCP のとき）

### レシピ（`recipes`）

| 列 | 内容 |
|---|---|
| `id` | ULID |
| `household_id` | 世帯 |
| `title` | 料理名（1〜200 文字） |
| `url` | レシピのリンク（任意。http/https のみ、2000 文字まで） |
| `body` | 自由テキスト（任意。材料、手順、変えたところなど。2 万文字まで） |
| `book_id` | 出典の本（任意。外部キー、`ON DELETE SET NULL`） |
| `page` | 本のページ（任意。`42`、`42-43` など 20 文字まで。本がある時だけ） |
| `added_by` | 追加した利用者 |
| `created_at`, `updated_at` | 時刻 |

- サーバーはリンク先を取得しない。中身が要る時は、アシスタントが自分でページを読む。ツールの説明で、ページ全体を写さず、リンクを出典として残し、世帯が覚えておきたいこと（変更点、要点）だけを書くよう促す。
- 一覧は更新の新しい順。検索はタイトルと本文の部分一致（`LIKE`、`%` と `_` は文字として扱う）。一覧には本文を含めない（アシスタントは `withBody` で含められる）。
- 変更履歴は持たない（`item_events` のような追記ログは、必要になってから足す）。

### 出典の本（`books`）とタグ（`recipe_tags`）

レシピのまとめ方は、出典とタグの 2 つにする。出典はレシピに 1 つで、ページのような付随情報を持つため、タグとは分ける。フォルダ（1 か所にしか入らない）は、1 つのレシピが「本 A」「主菜」「作り置き」に同時に入るので使わない。key=value は付け方が揺れるので使わない。

- 出典は、リンク（`url`）か、本（冊子、雑誌を含む）とページ。本は `books`（`id`、`household_id`、`title`、`created_at`。世帯内で `title` は一意）で、レシピからは名前で指定する（同じ名前の本があれば使い、なければ足す）。本の名前を変えると、そのレシピすべての表示が変わる。本を削除しても、レシピは残る（本とページだけ消える）。
- 写真そのものは保存しない。アシスタントが写真から書き起こし、本とページを出典として残す。
- タグは `recipe_tags`（`recipe_id`、`household_id`、`tag`。主キーは `recipe_id` と `tag`）で、タグ自体の表は持たない（どれかのレシピに付いている間だけ存在する）。1〜30 文字で、空白と読点は含めない（1 つの入力欄にスペース区切りで書けるように）。先頭の `#` は落とす。1 レシピに 20 個まで。
- 観点は、種類（主菜、副菜など）、手間・調理法（時短、レンジなど）、保存（作り置き、冷凍可など）、季節。食材や調味料は種類が多すぎるので、タグにせず本文の検索で探す。この案内はツールの説明に書き、決まった一覧は持たない。表記の揺れは、既存のタグを選べる UI（Web）、`list_tags` で既存を確かめるよう促す説明（MCP）、`rename_tag`（同じ名前への変更は統合になる）で抑える。
- 「作ってみたい」「定番」はタグにしない。作った記録から分かる（まだ作っていない、何度も作っている）ので、手で付けると記録と食い違う。
- 一覧はタグ（複数指定は AND）と本で絞り込める。

### 作った記録（`recipe_cooks`）

どのレシピを、どの日に作ったか。繰り返し調理率の計測（段階 0）と、アシスタントが「最近作っていないもの」などを提案する材料にする。

| 列 | 内容 |
|---|---|
| `id` | ULID |
| `household_id` | 世帯 |
| `recipe_id` | レシピ（外部キー、`ON DELETE SET NULL`）。レシピを削除しても記録は残る |
| `title` | 記録した時点の料理名のスナップショット |
| `cooked_on` | 作った日（`YYYY-MM-DD`、作った人のその土地の日付）。時刻ではないので Unix 秒にしない |
| `note` | ひとこと（任意。2000 文字まで） |
| `user_id`, `source`, `client_id` | 誰が、どこから（`web` / `mcp`）記録したか |
| `created_at` | 記録した時刻 |

- 日付はサーバーの時計で決めない（Web はブラウザのその日、MCP はアシスタントが渡す）。存在しない日付（2 月 30 日など）は拒否する。
- レシピの一覧と取得には、作った回数（`cookCount`）と最後に作った日（`lastCookedOn`）を付ける。
- レシピに紐づかない「食べたもの」（外食、買ったもの）の記録は、まだ扱わない。

### 世帯と認証

`households`、`users`、`memberships`（役割は `admin` / `member`。多対多にしておき、最初の UI は 1 利用者 1 世帯）、`passkeys`、`sessions`、`invites`、`challenges`（WebAuthn のチャレンジ）、`app_meta`、`oauth_clients`、`oauth_codes`、`oauth_tokens`。詳しくは `src/db/schema.ts`。

## MCP ツール

最新の仕様（2026-07-28: セッションなし、リクエストごとの `_meta` とヘッダーの照合、`server/discover`）と、旧版（`initialize` を受けるがセッションは発行しない）の両方に対応する。実機の claude.ai は最新の仕様で接続した。ChatGPT（無料プラン、プラグイン画面のカスタム MCP、dev mode）も、動的クライアント登録（DCR）と OAuth で接続でき、チャットからの読み書きが通った。事前登録は不要だった。

`initialize` と `server/discover` の応答に `instructions`（サーバー全体の使い方、英語）を付ける。中身は、何のデータか、変更は家族にすぐ見えること、「何ができる？」や初回には先に冷蔵庫とレシピを見てその家に合った頼み方を 3 つほど挙げること、レシートの写真の扱い、まとめて消す前の確認、返事の言語。クライアントが渡すとは限らないので、各ツールに要る決まりはツールの説明にも残す。リクエストごとに、メソッド、ツール名、クライアント名、プロトコルの版だけを 1 行のログに出す（引数は出さない）。各アシスタントが実際に何を呼ぶか（`instructions` を受け取るメソッドを呼ぶか）を確かめるため。

| ツール | 内容 | スコープ |
|---|---|---|
| `list_items` | リストと状態で絞り込んで一覧 | `read` |
| `get_item` | 1 件取得 | `read` |
| `create_item` | 追加（初期状態は `to_buy` / `in_stock`） | `write` |
| `update_item` | 品名、状態、メモの更新 | `write` |
| `delete_item` | 削除 | `write` |
| `move_item` | 別のリストへ移動 | `write` |
| `list_item_history` | 変更履歴の取得 | `read` |
| `list_recipes` | レシピの一覧（検索、タグ、本で絞り込み。本文を含めるかを選べる） | `read` |
| `get_recipe` | 1 件取得（本文、出典、タグ、作った回数、最後に作った日） | `read` |
| `create_recipe` | 追加（料理名、リンク、本とページ、タグ、本文） | `write` |
| `update_recipe` | 更新（指定した項目だけ。タグは全体を置き換える） | `write` |
| `delete_recipe` | 削除（作った記録は残る） | `write` |
| `record_cook` | 作った記録をつける（日付は `YYYY-MM-DD`） | `write` |
| `list_cooks` | 作った記録の一覧（レシピ、日付で絞り込み） | `read` |
| `delete_cook` | 作った記録の削除 | `write` |
| `list_tags` | 使っているタグ（多い順、件数付き） | `read` |
| `rename_tag` | タグの名前の変更（既存のタグへの変更は統合） | `write` |
| `list_books` | 出典の本（名前順、件数付き） | `read` |
| `rename_book` | 本の名前の変更 | `write` |
| `delete_book` | 本の削除（レシピは残る） | `write` |

`tools/list` の中身は、ビルド時に JSON へ直列化しておく（`pnpm gen` で `src/mcp/tools.generated.ts` を作り直す。ツールを変えて生成し忘れると、テストが失敗する）。実行時に zod のスキーマを変換すると、アイソレートの最初の 1 回に 3〜10 ms の CPU がかかり、Workers Free の 10 ms の大半を使うため。説明文には、状態名の意味と「状態の変更は移動しない」ことを書く。読み取り専用のツールには `readOnlyHint` を付け、削除には `destructiveHint` を付ける。

## テスト方針

- **モックはほとんど使わない。** 自前のコード（サービス、認証、OAuth）は本物を使う。
- **単体テストでは、DB のモックを認める。** 結合テストでは DB も本物を使う（実際の SQLite〔`node:sqlite`〕に本物のマイグレーションを当てる）。DB を使う処理は制約やトランザクションの挙動が結果を左右するので、本物を使う結合テストで確かめる。
- DB 以外でモックを認めるのは、どうしても必要な外部依存だけ（例: 外部のネットワーク、ブラウザの認証器）。使うときは、なぜ必要かをテストの近くにコメントで書く。
- 時刻と ID の生成は、モックではなく注入する引数（`now`、`newId`）で固定する。
- 層ごとの役割:
  - 単体: 純粋なロジック（ハッシュ、PKCE、`redirect_uri` の照合、スコープの絞り込み）。
  - 結合: Hono のアプリを `app.request()` で呼び、実際の SQLite をつなぐ。OAuth の流れ、世帯の分離、最初の管理者の競合を確認する。
  - E2E（HTTP）: `pnpm e2e`。MCP の流れ（DCR から `tools/call` まで）を HTTP 越しに通す。
  - E2E（ブラウザ）: `pnpm test:browser`。Playwright と Chrome の仮想認証器で、セットアップ、リスト操作、ログアウトと再ログイン、招待、アシスタントの接続（同意、トークン、MCP、解除）、インストール要素を本物のブラウザで通す。ビルド済みのアプリと Node 版を、使い捨ての DB で起動する。
  - 実際の claude.ai と ChatGPT との接続確認は手で行う。
- D1 固有の挙動（`batch`、外部キー、CPU 10 ms）は、D1 向けの `wrangler dev` と実機の計測で確認する。
